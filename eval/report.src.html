dsh-plan-checkup · M2 評測報告

計畫體檢 M2 評測

用 300 份合成計畫比較兩種判斷引擎。區網 vLLM 上的 Qwen3.8-27B 讀選項機率，在沒看過的測試情境上，英文題目下六個標記的 F1 在 0.85 到 1.00；預訓練的 Laya 幾乎分不出好壞，要用就得微調。

資料 300 份計畫、1,415 步 引擎 Qwen3.8-27B（區網 vLLM）、Laya 0.3.22（本機 GPU） 插件 dsh-plan-checkup 0.1.0-m2 日期 2026-09-30

§1結論

建議

  1. 主要引擎用區網的 Qwen3.8-27B（插件的 engine: llm，英文題目）。保留測試集上：無法復原、影響外部、需求沒提到、沒有驗證步驟四項的 F1 都是 1.00；描述太模糊 0.85；可能漏了需求 0.89。
  2. 預訓練的 Laya 不能直接用。保留測試集上各題的 AUROC 只有 0.43 到 0.68；自動分流時「無法復原」的精確率只有 0.07。要用 Laya 就要微調，做法見 §6。
  3. 規則要保留，但不能只靠規則。規則的精確率是 1.00，可以當沒有引擎時的底線；只靠規則的話，保留測試集的「無法復原」只抓到 35%，「影響外部」只抓到 13%。
  4. 題目維持英文。中文題目在其他題目上和英文差不多，但「可能漏了需求」的召回率明顯較低。
  5. 門檻調整三項：無法復原 0.7 → 0.6、需求沒提到 0.6 → 0.4、描述太模糊 0.7 → 0.8，另外「會改程式」0.6 → 0.4。開發集還挑出兩項候選（影響外部 0.8、漏了需求 0.6），在保留測試集上沒有改善，不採用。
  6. 選項正反各問一次（swapOptions）維持關閉。和單一順序相比，機率平均只差 0.006 到 0.023；保留測試集上只有「可能漏了需求」從 0.89 變成 0.91，其他五項完全一樣，請求數和時間卻都加倍。

這一輪也改了插件本身：四題的判斷說明，以及兩條合成規則。其中一條修掉第一輪發現的 bug：只要有步驟提到「測試」，就不會提醒「沒有驗證步驟」。改動都在 §4，對應的單元測試已經補上。

§2資料與方法

沒有真實的計畫模式紀錄，所以評測資料是合成的。每個情境有一句需求、幾個必要步驟、驗證步驟，以及刻意埋進去的問題步驟：需求沒要求的工作、無法復原的操作、影響外部的操作、描述模糊的步驟。程式用固定的 seed 把它們組成計畫，每一步的標準答案在組合時就決定了。

  • 開發集：14 個情境、210 份計畫、1,001 步。用來找錯誤、改題目和挑門檻。
  • 保留測試集：6 個情境、90 份計畫、414 步，情境、步驟文字和共用步驟庫都和開發集不同。第一輪看完錯誤之後才寫，改題目、挑門檻時都沒有用到，最後的數字以它為準。
  • 兩份資料的繁中、簡中、英文各占三分之一。
  • 情境和步驟由我撰寫，沒有讓 Qwen 出題，避免它考自己寫的題目。

標註準則寫在 eval/LABELS.md。判斷不了的標成「不計分」，例如「部署到正式環境」算不算需求沒提到，要看團隊習慣。準則裡也列了五種刻意放的陷阱：

  • 提到「測試」但不是驗證步驟。
  • 刪除有進版控的檔案。
  • 需求本來就要求的危險步驟。
  • 通常算多做、但需求明確要求的工作。
  • 規則認不得的危險敘述。

評測程式直接呼叫插件的 runCheckup，送出的題目、內容格式和遮罩都和產品一樣。每個引擎跑完整份資料，再和標準答案比對：

  • AUROC：機率能不能把「是」排在「否」前面。0.5 等於亂猜，1.0 是完全分開。
  • ECE：機率和實際比例差多少。越小越準。
  • 精確率與召回率：看的是卡片上真正會出現的標記，也就是規則和引擎合起來的結果。

§3保留測試集的結果

F1 或 AUROC ≥ 0.850.60–0.85< 0.60

Qwen 在前四題的 AUROC 都是 1.00：每個「是」的機率都高於每個「否」，判錯只會出在門檻的位置。比較弱的是「可能漏了需求」，AUROC 0.94 到 0.95。這一題要拿需求的每個部分去對照所有步驟，比判斷單一步驟難。

剩下的錯誤都有明確的樣子：

  • 「重新產生正式環境所有舊圖的縮圖並覆蓋舊檔」的無法復原機率是 0.62–0.68。縮圖本來就能重新產生，這題算不算無法復原本身有爭議；新門檻 0.6 會把它標出來。
  • 「重新整理 test/ 資料夾的檔案結構」被判成描述太模糊（0.80–0.87）。它沒說新結構是什麼，和開發集裡改成「不計分」的「整理成新的目錄結構」屬於同一類。
  • 「需求沒提到」漏掉的步驟，模型其實都選了「多做」，只是機率在 0.47–0.58。門檻降到 0.4 之後全部抓回來，精確率仍是 1.00。

§4第一輪之後改了什麼

第一輪用 M1.5 的題目跑開發集，看完錯誤後改了三類東西。改完的版本叫第二版題目，保留測試集只用第二版跑。

題目說明

  • 無法復原：刪除有進版控的檔案不算。舊說明把「刪除既有的檔案」列為例子，模型照著判，刪除原始碼的步驟有 41% 被誤判。
  • 影響外部：寫出上線後才會寄信的程式、只讀取遠端資料，都不算。「寫一個會寄出重設連結的 API」原本被誤判了 14 次。
  • 描述太模糊：說清楚要做什麼就不算，不必寫出檔名。舊說明要求「指出檔案、函式或指令」，所以「部署到正式環境」這種步驟都被當成模糊。
  • 可能漏了需求：補上判斷標準。

合成規則

  • 「沒有驗證步驟」：引擎有回答時以引擎為準。規則會把「更新測試資料」「簡訊驗證碼」也當成驗證，第一輪 17 份這類計畫只提醒了 1 份。
  • 「需求沒提到」改看「多做」這個選項的機率，不看 confidence。Laya 的 confidence 遠低於最高的機率（0.31 對 0.66），只有機率本身在各引擎間意思一樣。

標註

  • 產生器的 bug：想標「不計分」的欄位被 ?? 轉成 0。
  • 「拆表」情境的需求從「移到新表」改成「複製到新表、舊欄位先保留」。「移到」也可以讀成要刪舊欄位，沒有刪欄位步驟的計畫都像漏了需求。
  • 把改動上線的步驟（推到 main、部署、發布、重啟正式服務）不再判「需求沒提到」，只判「影響外部」。

「可能漏了需求」的召回率在第二輪反而下降（0.69 → 0.46，門檻 0.7）：新的說明讓模型比較保守。保留測試集上它的 F1 是 0.89（英文題目），所以維持 0.7，沒有為了開發集往下調，見 §8。

§5規則與判斷引擎各做了什麼

規則只認指令，例如 DROP TABLE、git push --force，中文敘述它一律看不見：「刪掉正式資料庫裡超過三年的訂單」「用正式環境的寄信帳號寄給全公司」都要靠引擎。以採用的門檻計算，保留測試集裡規則沒抓到的危險步驟，英文題目下引擎全部補上了；中文題目「無法復原」補上 13 步裡的 12 步。

反過來，規則命中時一定是對的（精確率 1.00），而且不需要連線，所以留著當底線：引擎停擺、逾時或沒設定時，卡片照樣會出現這些標記。

§6Laya：預訓練版不能用，要用就得微調

Laya 0.3.22 有三個預訓練版本，都在本機的 RTX 5060 Ti 上跑，一份計畫的中位數約 0.16 到 0.26 秒：

  • english：ModernBERT-large。
  • multilingual：mmBERT-base，322M 參數。
  • typed-decisions：官方用四種工作流程微調過的英文版。

它的伺服器直接相容 Jev 的格式，插件不用改程式，把 engine: jev 的端點指到本機就能用。

結果不能用：

  • 自動分流（中文走 multilingual，英文走 english）幾乎每一步都標：保留測試集上「無法復原」多標了 220 步，精確率 0.07。
  • typed-decisions 反過來，機率都擠在 0.5 附近，什麼都不標；卡片上看到的只剩規則的結果。
  • AUROC：保留測試集上各題在 0.43 到 0.68 之間，開發集 0.37 到 0.79，也就是機率本身就分不出好壞。

這和 Laya 自己的說明一致：基礎版不微調時，在它的 typed-decisions 基準上是 0.362，還低於永遠猜最多的那一類（0.461）。

要不要微調

要用 Laya 就一定要微調。校準溫度只能修正機率的尺度，AUROC 接近 0.5 的問題它修不了。

  • 可以在本機做：你的 RTX 5060 Ti（16 GB）足夠訓練 322M 的 multilingual 版，資料不用上傳到 Kaggle。
  • 要自己改訓練程式：pip 套件只帶了校準工具，訓練要用 Laya repo 裡為 Kaggle 寫的 notebook，改成本機執行。
  • 資料現成：開發集的 210 份計畫約有 5,300 個有答案的判斷，和官方 typed-decisions 用的 2,000 筆同一個量級；保留測試集拿來驗證泛化。要更多資料，可以用 Qwen 的機率當軟標籤去標更多計畫。
  • 工夫：估計半天到一天，含改 notebook、訓練、評測。

值不值得做，要看給誰用。你有區網的 Qwen，Laya 對你沒有額外的好處；它的價值在於給沒有 GPU 伺服器的使用者一個筆電就能跑、完全不外送的選項。這件事可以排在發布（M3）之後。

§7延遲、重跑與選項順序

  • 延遲：英文題目一份計畫的中位數 2.1 秒、p95 2.9 秒。平均每份 4.8 步、26 個請求、約 7,200 個輸入 token，中文題目幾乎一樣。卡片在 0.5 秒內先顯示規則的結果，之後每檢查完一步就更新一次。
  • 重跑：同一設定再跑 60 份，機率平均只差 0.001 到 0.006，95% 的差距在 0.03 以內，卡片上的標記完全相同。溫度設為 0 時，區網 vLLM 的輸出很穩定。
  • 選項順序：每題正反各問一次再平均，和單一順序相比，機率平均差 0.006 到 0.023，只有 0.17% 的標記改變。M1.5 用單份計畫探測時，模糊的題目曾差到 0.2；題目說明改清楚之後，這種模稜兩可的情況少了很多。
  • 題目語言：英文題目和中文題目的機率平均差 0.016 到 0.043。差最多的是「可能漏了需求」：開發集的 F1 英文 0.59、中文 0.31。

§8門檻

門檻在開發集上用 Qwen 英文題目挑：畫出每一題「門檻對 F1」的曲線，取高原區裡較穩的點，「無法復原」偏向召回率。挑好之後才拿保留測試集驗證，沒有改善的就維持原值。

「影響外部」0.8 在開發集稍好（F1 0.986 → 0.995），但保留測試集用中文題目時召回率從 1.00 掉到 0.90；這一項漏報的代價比誤報高，所以維持 0.7。「可能漏了需求」0.6 在開發集較好，保留測試集英文題目卻從 0.89 掉到 0.70，也維持 0.7。這組門檻是依 Qwen3.8-27B 校準的，換模型或換成 Jev 要重新量。

機率本身的準度：Qwen 各題的 ECE 在 0.01 到 0.13，只有「可能漏了需求」是 0.24 到 0.35。擬合出來的溫度是 0.5 到 0.7，代表機率偏保守，拉開之後 ECE 會再小一點，但排序不變。門檻是在溫度 1 的機率上挑的，所以 llm.temperature 維持 1。

§9限制與下一步

  • 合成資料偏乾淨。同一段步驟文字會出現在好幾份計畫，兩份資料裡不同的步驟文字只有 470 段；真實的計畫更長、更雜，也會有兩件事寫在同一步。這裡的分數應該當成上限。
  • 「可能漏了需求」最弱。它是整份計畫層級的判斷，建議當成較弱的提醒；要改善，可能需要先把需求拆成條列再逐條對照，這要用到生成，不是單一選擇題做得到的。
  • Jev 沒有量。沒有金鑰。拿到後用同一套資料跑 engine: jev，門檻要另外校準。
  • 真實資料會自己累積。插件的 ledger.jsonl 記下每次體檢的機率、你的決定和每個標記的讚／倒讚，用一陣子之後可以拿來重新校準。

下一步是 M3：發布 npm、三種語言的 README、上架插件商店。Laya 微調可以排在 M3 之後，視有沒有「筆電就能跑」的需求再決定。
